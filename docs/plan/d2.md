- [x] **D2.3 Policy engine.** (6d4af4a..060d101 plus this close commit; scoped typecheck for contracts, core and server, biome on the touched paths, the `@mawl/core` suite (1415 passed) and the server `policy.pglite` file; reviewer approved and head-reviewer approved with follow-ups, its three majors fixed; turbo gate, Docker suites and e2e not run.) Action classes, levels, rule precedence, and the non-lowerable classes. *Tests:* a table-driven rule-matrix test.
  - *From D2.2 review:* `web_fetch` must not be plain `auto`: a model-chosen url query can exfiltrate data (context, secrets the model saw) and the `run.tool_call` event redacts the query, so the owner cannot see what left. Decide a level or a host rule for it. The address guard cannot stop fetches to the host's own public IP or to router UIs reached through hairpin NAT; account for that in the rules.
  - *Outcome (D2.3):* first fetch to a host in a run is `ask`, later ones to that host `auto`, allow-listed hosts `auto`, local and private hosts `block`. Allowed and seen hosts are keyed by host name only, so they match any port and both schemes. **Hairpin NAT is not detected** (known gap): a fetch to the host's own public IP looks public to both the policy and the egress guard, and no code can see the router send it back into the LAN. The mitigation is the first-host `ask`, where the owner sees the host on the approval card; allow-listed and Autopilot fetches skip it.
  - *Added 2026-10-24 (R16):* rules match on the node kind too. The `this_pc` defaults go in the matrix from the start: reads in a grant `auto`, writes in a grant `ask` (lowerable per grant), `shell_exec` `ask` (lowerable only by an exact command-prefix rule), `delete` never below `ask`. A `teammate` trigger never carries the owner's approval (R19).

The Needs you tab of `/approvals` reads two queries: `approvals.list {status:'pending'}` (the "Waiting for you" group, the all-caught-up empty state and the sidebar badge count) and `approvals.list {limit:50}` (the "Recent" group, resolved rows only). `ApprovalCard` shows tool, teammate, action class, Mawl's reason, the redacted args, a countdown (`Expires in 30 min`, `Expiring now` once past `expiresAt` until the server's minute sweep resolves it) and Approve / Deny; resolved cards show a status badge (approved, denied, expired, cancelled) and the time. The chat shows the same card (`RunApprovals`, with a link to the inbox) for the followed run while it is active, so a decided card stays visible as the run continues; if the call cannot be loaded, a note links to the inbox. A `waiting_approval` run shows the card instead of the thinking dots. No contract or event-store change: `approval.*` events already invalidate the approvals queries. Not done: the Activity tab (D2.12), approving from Telegram/Discord, decision undo.

  - *From the D2.3 head review:* (a) redirect hops in `web_fetch` bypass the policy: an open redirect on an allowed or seen host can carry data to an unapproved host; re-check a cross-host hop against `allowedHosts` and the seen hosts, else stop with a note.
